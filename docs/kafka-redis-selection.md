# Kafka와 Redis를 함께 선택한 이유

> 참고: [AWS, Kafka와 Redis OSS의 차이점은 무엇인가요?](https://aws.amazon.com/ko/compare/the-difference-between-kafka-and-redis/)

## 들어가며

이 프로젝트는 증권 거래 시스템을 단순 CRUD로 구현하는 것이 아니라, 주문, 잔고, 체결, 시세처럼 성격이 다른 데이터를 어떻게 안전하고 빠르게 다룰지 실험하기 위한 토이 프로젝트입니다.

특히 증권 거래 도메인에서는 모든 데이터를 같은 방식으로 처리하기 어렵습니다. 주문 접수 이벤트는 잃어버리면 안 되고, 체결 이벤트는 재처리할 수 있어야 하며, 시세와 대시보드 조회는 매우 빠르게 응답해야 합니다. 그래서 이 프로젝트에서는 Kafka와 Redis를 경쟁 관계의 기술로 보지 않고, 서로 다른 문제를 해결하는 도구로 나누어 선택했습니다.

AWS 비교 글에서도 Kafka는 스트림 처리 엔진, Redis는 인메모리 키-값 데이터 스토어로 설명합니다. 둘 다 게시/구독 구조에 사용할 수 있지만, Kafka는 메시지를 보존하고 소비자가 가져가는 구조에 강점이 있고, Redis는 메모리 기반의 매우 낮은 지연 시간에 강점이 있습니다. 이 차이가 이 프로젝트의 기술 선택 기준이 되었습니다.

## 프로젝트에서 해결하려는 문제

이 시스템의 핵심 요구는 크게 네 가지입니다.

첫째, 주문 요청은 유실되면 안 됩니다. 사용자가 매수 주문을 넣었는데 시스템 내부 이벤트 발행 실패로 이후 단계가 진행되지 않으면 치명적입니다.

둘째, 잔고 예약과 주문 접수는 하나의 정합성 경계 안에서 처리되어야 합니다. 현재 구현에서도 `OrderService`는 주문 생성, 잔고 예약, outbox 이벤트 저장을 하나의 트랜잭션으로 묶고 있습니다.

셋째, 체결, 알림, 조회 모델 갱신 같은 후속 처리는 주문 접수 API와 느슨하게 분리되어야 합니다. 주문 API가 모든 후속 작업을 동기적으로 처리하면 응답 시간이 길어지고 장애 전파 범위도 커집니다.

넷째, 조회는 쓰기 모델과 다른 방식으로 최적화되어야 합니다. 주문/잔고의 원천 데이터는 PostgreSQL에 두되, 시세성 데이터나 자주 조회되는 화면 데이터는 Redis 같은 빠른 저장소를 활용할 수 있어야 합니다.

## Kafka를 선택한 이유

Kafka는 이 프로젝트에서 이벤트 스트리밍과 비동기 처리의 중심 역할을 맡습니다. 주문이 접수되면 `OrderAccepted` 이벤트가 outbox에 저장되고, 이후 별도 퍼블리셔가 Kafka로 발행하는 구조를 의도하고 있습니다.

Kafka를 선택한 가장 큰 이유는 메시지 보존과 재처리 가능성입니다. AWS 글에서 설명하듯 Kafka는 소비자가 메시지를 읽은 뒤에도 보존 정책에 따라 메시지를 유지할 수 있습니다. 이 특성은 주문, 체결, 잔고 변경처럼 복구와 감사가 중요한 이벤트에 잘 맞습니다. 컨슈머 장애가 발생해도 마지막으로 처리한 offset 이후부터 다시 읽을 수 있고, 버그가 있는 컨슈머를 수정한 뒤 특정 구간의 이벤트를 재처리하는 전략도 세울 수 있습니다.

두 번째 이유는 소비자 그룹을 통한 확장성입니다. 주문 접수 이후에는 체결 엔진, 읽기 모델 프로젝터, 알림 서비스, 감사 로그 저장소처럼 여러 후속 소비자가 생길 수 있습니다. Kafka는 같은 이벤트 스트림을 여러 소비자 그룹이 독립적으로 읽을 수 있어, 기능이 늘어나도 주문 접수 흐름과 후속 처리를 분리하기 좋습니다.

세 번째 이유는 순서 보장 전략입니다. 이 프로젝트의 아키텍처 문서에서는 Kafka 파티션 키를 `symbol`로 가져가는 방향을 남겨두었습니다. 인기 종목에 주문이 몰리는 상황에서도 종목 단위로 이벤트 순서를 다룰 수 있고, 파티션을 늘려 처리량 확장 실험을 하기 좋습니다.

마지막으로 Kafka는 outbox pattern과 잘 맞습니다. DB 트랜잭션 안에서 주문과 outbox 이벤트를 함께 저장하고, 별도 프로세스가 outbox를 읽어 Kafka에 발행하면 "DB에는 반영됐는데 이벤트는 사라지는" 상황을 줄일 수 있습니다. 증권 거래처럼 정합성이 중요한 시스템에서는 이 점이 단순한 성능보다 더 중요합니다.

## Redis를 선택한 이유

Redis는 이 프로젝트에서 이벤트의 원장 역할이 아니라 빠른 조회와 짧은 수명의 상태 관리 역할에 더 적합합니다.

AWS 글에서 Redis는 RAM 기반으로 동작하기 때문에 매우 낮은 지연 시간에 강하다고 설명합니다. 이 특성은 시세, 호가, 사용자 대시보드, 주문 상태 요약처럼 자주 조회되고 빠른 응답이 중요한 데이터에 잘 맞습니다. 원천 데이터는 PostgreSQL과 Kafka 이벤트 흐름에 두고, Redis는 읽기 모델의 응답 속도를 높이는 캐시 또는 임시 저장소로 활용할 수 있습니다.

예를 들어 이 프로젝트가 확장되면 다음과 같은 데이터는 Redis에 두기 좋습니다.

- 종목별 최신 가격 또는 호가 스냅샷
- 계좌별 주문 상태 요약
- 대시보드용 최근 체결 목록
- API 중복 요청 방지를 위한 짧은 TTL의 멱등성 키
- WebSocket이나 실시간 조회 화면을 위한 임시 상태

다만 Redis를 Kafka 대신 핵심 이벤트 버스로 사용하지는 않습니다. Redis pub/sub은 즉시 전달에는 빠르지만, 기본적으로 메시지 보존과 재처리 측면에서 Kafka보다 약합니다. 구독자가 없는 동안 발행된 메시지는 복구하기 어렵고, 장애 이후 특정 시점부터 이벤트를 다시 읽는 구조에도 적합하지 않습니다. 주문 접수나 체결 이벤트처럼 잃어버리면 안 되는 데이터에는 이 한계가 큽니다.

따라서 Redis는 "정답을 저장하는 곳"이 아니라 "정답을 빠르게 보여주기 위한 곳"으로 둡니다. 캐시가 비거나 오래되면 PostgreSQL 또는 Kafka 기반 프로젝션을 통해 다시 만들 수 있는 데이터에 한정해서 사용하는 것이 이 프로젝트의 방향입니다.

## Kafka와 Redis의 역할 분리

이 프로젝트에서 두 기술의 역할은 다음처럼 나눌 수 있습니다.

| 구분 | Kafka | Redis |
| --- | --- | --- |
| 주된 목적 | 이벤트 스트림, 비동기 처리, 재처리 | 캐시, 빠른 조회, 짧은 수명의 상태 |
| 데이터 성격 | 잃어버리면 안 되는 도메인 이벤트 | 다시 만들 수 있는 조회 데이터 |
| 처리 방식 | 소비자가 offset 기준으로 pull | 메모리 기반 빠른 read/write |
| 장애 대응 | 메시지 보존, 재처리, consumer group | TTL, 캐시 재생성, 임시 상태 복구 |
| 프로젝트 예시 | `OrderAccepted`, 체결 이벤트, 읽기 모델 갱신 이벤트 | 최신 시세, 주문 요약, 대시보드 캐시 |

즉, Kafka는 시스템 내부의 사건을 안정적으로 흘려보내는 로그이고, Redis는 사용자가 자주 보는 화면을 빠르게 만들기 위한 가속 계층입니다.

## 왜 Kafka 하나만 쓰지 않았나

Kafka는 이벤트 스트림에는 강하지만, 사용자 요청마다 최신 조회 데이터를 낮은 지연 시간으로 꺼내는 저장소로 쓰기에는 적합하지 않습니다. 컨슈머가 이벤트를 읽어 별도 조회 모델을 만들 수는 있지만, API가 매번 Kafka를 직접 조회해서 화면 데이터를 만드는 구조는 자연스럽지 않습니다.

주문 내역, 대시보드, 시세성 데이터는 사용자가 반복적으로 조회합니다. 이런 데이터는 Redis에 미리 계산된 형태로 저장해두면 API 응답을 단순하고 빠르게 만들 수 있습니다. Kafka는 Redis에 들어갈 읽기 모델을 만드는 이벤트 공급원이 되고, Redis는 그 결과를 빠르게 제공하는 역할을 맡습니다.

## 왜 Redis 하나만 쓰지 않았나

Redis는 빠르지만, 이 프로젝트의 핵심 이벤트 저장소로 삼기에는 부족합니다. 주문 접수, 체결, 잔고 반영 이벤트는 장애가 나도 복구할 수 있어야 하고, 컨슈머가 실패하면 다시 처리할 수 있어야 합니다. 또한 나중에 알림, 감사, 정산, 통계처럼 새로운 소비자가 추가될 수 있습니다.

Kafka는 메시지 보존, offset 기반 처리, consumer group, 파티션 기반 확장 같은 특성 때문에 이런 이벤트 중심 구조에 더 잘 맞습니다. Redis만으로 구현하면 초반에는 단순해 보일 수 있지만, 장애 복구와 재처리 요구가 생기는 순간 애플리케이션 코드가 복잡해질 가능성이 큽니다.

## 현재 구현과 앞으로의 연결

현재 프로젝트에는 PostgreSQL, Redis, Kafka를 로컬에서 실행할 수 있는 `docker-compose.yml` 구성이 들어 있습니다. 애플리케이션 코드에서는 주문 접수 시 `outbox_events` 테이블에 `OrderAccepted` 이벤트를 저장하는 구조가 먼저 구현되어 있습니다.

앞으로의 구현 방향은 다음과 같습니다.

1. Outbox publisher가 `published = false` 이벤트를 읽어 Kafka topic으로 발행합니다.
2. Kafka consumer가 주문 이벤트를 받아 체결 흐름 또는 읽기 모델 갱신을 수행합니다.
3. 조회 모델 프로젝터가 Kafka 이벤트를 소비해 Redis 캐시를 갱신합니다.
4. API 조회는 PostgreSQL 원장 데이터와 Redis 조회 데이터를 목적에 맞게 나누어 사용합니다.
5. 컨슈머 장애, 중복 이벤트, 재처리 시나리오를 테스트로 보강합니다.

이 흐름에서는 PostgreSQL이 정합성의 기준점, Kafka가 이벤트 전달과 재처리의 중심, Redis가 빠른 조회를 위한 보조 저장소가 됩니다.

## 정리

이 프로젝트에서 Kafka와 Redis를 함께 선택한 이유는 두 기술이 해결하는 문제가 다르기 때문입니다.

Kafka는 주문과 체결처럼 잃어버리면 안 되는 이벤트를 안정적으로 전달하고, 장애 이후에도 재처리할 수 있게 해줍니다. Redis는 자주 조회되는 데이터를 메모리에 올려 낮은 지연 시간으로 응답하게 해줍니다.

증권 거래 시스템에서는 정합성과 속도 중 하나만 선택할 수 없습니다. 쓰기 흐름에서는 정합성과 복구 가능성을 우선하고, 읽기 흐름에서는 빠른 응답과 확장성을 우선해야 합니다. Kafka와 Redis를 함께 사용하는 이유는 바로 이 경계를 코드와 인프라에 명확히 드러내기 위해서입니다.
