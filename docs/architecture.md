# Architecture Notes

## 1. 프로젝트 목표

이 시스템은 실제 증권사 수준의 완성도를 목표로 하지는 않지만, 다음과 같은 설계 감각을 체험하는 데 초점을 둡니다.

- 주문 요청은 잃어버리면 안 된다.
- 잔고 차감은 틀리면 안 된다.
- 조회는 빠르고 많이 들어와도 버텨야 한다.
- 같은 이벤트가 두 번 처리되어도 결과가 망가지지 않아야 한다.

## 2. 핵심 도메인

### 주문(Order)

- 사용자가 매수/매도 주문을 제출한다.
- 주문은 접수, 예약, 부분 체결, 전량 체결, 취소 등의 상태를 가진다.
- 주문 요청은 멱등 키를 통해 중복 제출을 방지한다.

### 체결(Execution)

- 주문은 매칭 엔진에서 다른 주문과 체결될 수 있다.
- 체결은 주문과 분리된 불변 이벤트로 저장한다.
- 체결 이력은 추후 감사와 복구의 핵심 자료가 된다.

### 계좌(Account / Ledger)

- 현금 잔고와 보유 수량은 "현재 상태"만 저장하지 않고 원장성 기록을 남긴다.
- 주문 접수 시에는 사용 가능 잔고를 예약한다.
- 체결 확정 시에만 실제 원장 반영을 완료한다.

### 시세(Market Data)

- 시세/호가/체결가 조회는 읽기 트래픽이 많다.
- 원장 DB에 직접 붙기보다 캐시나 읽기 전용 모델로 분리하는 것이 좋다.

## 3. 아키텍처 방향

초기에는 모놀리식으로 시작하되, 내부 경계를 분리합니다.

- `order`: 주문 접수와 상태 관리
- `account`: 현금/주식 잔고와 예약 금액 관리
- `execution`: 체결 결과 기록
- `marketdata`: 시세성 조회 데이터
- `common`: 공통 응답, 예외, 이벤트

이 구조는 추후 다음처럼 확장 가능합니다.

- 주문 접수 API 서버
- 체결 엔진 프로세스
- 읽기 모델 프로젝터
- 알림/정산/감사 소비자

## 4. 정합성 전략

### 쓰기 모델

- 주문 접수와 잔고 예약은 하나의 로컬 트랜잭션으로 묶습니다.
- 핵심 원칙은 "주문이 접수됐는데 잔고 예약이 안 됨" 혹은 그 반대 상태를 만들지 않는 것입니다.
- 따라서 초기 단계에서는 `PostgreSQL`을 단일 정합성 소스로 둡니다.

### 이벤트 발행

- DB 반영 후 Kafka 발행이 실패하면 정합성이 깨질 수 있습니다.
- 이를 피하기 위해 `Outbox Pattern`을 사용합니다.
- 주문/잔고 트랜잭션 안에서 outbox 레코드까지 저장하고, 별도 퍼블리셔가 Kafka로 전달합니다.

### 중복 처리

- API 계층: `idempotency_key`
- Consumer 계층: `event_id` 기반 중복 처리
- 체결/원장 계층: 같은 명령 재적용 방지 키 보관

## 5. 성능 전략

### 조회와 쓰기 분리

- 계좌 원장, 주문 상태 변경은 쓰기 정합성이 우선
- 주문 내역 조회, 시세 조회, 대시보드 조회는 읽기 성능이 우선
- 따라서 읽기 모델은 비동기 프로젝션으로 분리 가능하게 설계합니다.

### 핫스팟 완화

- 인기 종목에 주문이 몰리는 상황을 가정합니다.
- 초기에 DB 락으로만 버티기보다, 종목 단위 큐/파티셔닝으로 확장 가능한 구조를 염두에 둡니다.
- Kafka 파티션 키를 `symbol`로 가져가면 종목별 순서 보장을 활용하기 쉽습니다.

### 대량 데이터

- 주문/체결 테이블은 빠르게 커집니다.
- 생성 시점 기준 파티셔닝, 보관 주기, 아카이빙 전략이 필요합니다.
- 이 프로젝트에서는 우선 단일 테이블로 시작하고, 이후 파티셔닝 실험 포인트를 남깁니다.

## 6. 추천 API 흐름

### 주문 접수

1. 사용자 인증/계좌 확인
2. 멱등 키 중복 확인
3. 주문 유효성 검증
4. 사용 가능 현금/수량 예약
5. 주문 생성
6. outbox 이벤트 저장
7. 커밋

### 체결 반영

1. 체결 엔진이 체결 이벤트 생성
2. 체결 이벤트 저장
3. 주문 상태 갱신
4. 잔고 원장 반영
5. 읽기 모델 갱신 이벤트 발행

## 7. 단계별 구현 제안

### Step 1

- 주문 접수 API
- 잔고 예약
- 주문/잔고/outbox 저장

### Step 2

- outbox 퍼블리셔
- 주문 이벤트 소비자
- 단순 모의 체결기

### Step 3

- 체결/잔고 조회 모델 분리
- Redis 캐시 도입

### Step 4

- 부하 테스트
- 락 전략 비교
- 장애/재처리 시나리오 실험
